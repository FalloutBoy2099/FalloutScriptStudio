# Fallout Script Studio — architecture

Rewrite of the legacy *Sfall Script Editor* (WinForms / .NET Framework 4.8 / ICSharpCode.TextEditor) as a
.NET 10 WPF application with the Fluent look of **WPF-UI** and the **AvalonEdit** text editor.

Step-by-step guides to extend it (menu commands, settings, languages, problems, editor commands, test files, options, publishing): [HOW_TO.md](HOW_TO.md).

## Projects

| Project | Target | Role |
|---|---|---|
| `FalloutScriptStudio.Core` | `net10.0` | Pure logic, no UI: parsing, compilation, message files, dialogue parsing, settings, refactoring, archives |
| `FalloutScriptStudio` | `net10.0-windows`, x86 | WPF application |
| `FalloutScriptStudio.ParserHost` | `net10.0`, x86, console | Hosts the optional 32-bit native `parser.dll` in its own process (see below); no UI, references Core |
| `FalloutScriptStudio.Core.Tests` | `net10.0` | Unit tests of Core, plus integration tests against the real sfall tools (skipped when absent) |
| `FalloutScriptStudio.Tests` | `net10.0-windows`, x86 | Unit tests of UI-side logic (router, editor helpers…) |

Dependencies: App → Core. Core never references WPF.

## Runtime layout (next to the executable, same as the legacy editor)

```
FalloutScriptStudio.exe
FalloutScriptStudio.ParserHost.exe                                                 (shipped: 32-bit process that runs parser.dll; built by Publish.ps1, copied by the build)
descriptions\   functions.ini, opcodes.txt, prochandlers.ini, userfunctions.ini   (content, copied from FalloutScriptStudio/Content)
resources\      mcpp.bat, wcc.bat, usercomp.bat, icon_*.ico, templates\*.ssl       (content)
                parser.dll                                                         (shipped: the sfall native parser, 32-bit; Content/resources)
                compile.exe (sslc), mcpp.exe, wcc386.exe                           (NOT shipped: user supplies them, all optional)
                int2ssl.exe, int2ssl_v35.exe                                       (optional: only for the "External int2ssl.exe" decompiler)
                syntax\Ssl.xshd, syntax\Msg.xshd                                   (optional: replace the built-in syntax highlighting definitions, same format as Assets/Syntax)
settings\       settings.json, recent.json, ... (created at runtime)
scrTemp\        scratch folder, wiped at start-up
```

No external tool is needed to **read `.dat` archives** (`FalloutScriptStudio.Core.Archives`: Fallout 1 and Fallout 2 formats, or a folder
standing in for an archive) or to **decompile `.int` scripts** (`FalloutScriptStudio.Core.Decompilation.BuiltInScriptDecompiler`, pure C#).
`undat`/`dat2` are gone. `int2ssl.exe` can still be plugged in: Settings > Compiler > Decompiler > "External int2ssl.exe" with an optional
path (`CompilerSettings.Decompiler` / `ExternalDecompilerPath`; `int2ssl_v35.exe` is the fallback, or the only tool with "Use the old decompiler").
Compilation still needs the user-supplied `compile.exe` (sslc); the preprocessors `mcpp`/`wcc` stay optional. `parser.dll` is shipped in `resources\` (a copy of the sfall one, identical to `_test_files\tools\parser.dll`); a user can still replace it by a newer sfall build, and the editor falls back to the built-in parser when it is missing or broken.

## Settings, scratch folder and instances

* `SettingsService` never writes blank defaults over real data: a file is saved only when this process changed it, and a file that
  changed on disk meanwhile (a second process, such as the stand-alone message editor) is merged property by property (three-way JSON
  merge against the content loaded). A file that exists but cannot be read (after a few retries) is neither taken for absent nor
  overwritten. `App.OnExit` saves only when `Load` completed.
* The scratch folder is prepared and deleted by the main editor only; the stand-alone message editor (`.msg` argument) shares it and never
  purges it. Leftovers that cannot be deleted are logged, never fatal (read-only attributes are cleared first).
* External tools get the scratch folder in the `FSS_SCRATCH` environment variable (`usercomp.bat` uses it); paths on their command lines
  are absolute, quoted and without a trailing backslash (except for a drive root, which is doubled).
* Intermediate preprocessed scripts are named `name_[pre]~<hash of the full path>.ssl`, so scripts of the same name in different folders can
  be compiled in parallel.

## Native parser (`parser.dll`) and the parser host

`parser.dll` is the 32-bit front end of the sfall compiler. It gives exact procedures, variables, references and includes, but it has
bugs that crash the process on ordinary half-typed scripts (a procedure declared twice, a procedure header with a missing comma), and an
access violation cannot be caught on .NET. **The application therefore never loads it.** `OutOfProcessNativeParser` (Core) talks to
`FalloutScriptStudio.ParserHost.exe`, which runs the in-process `NativeParser` engine:

* **Protocol**: JSON lines over stdin/stdout (`Core/Parsing/Interop/Host`: `HostProtocol`, `HostRequest`, `HostResponse`, source-generated
  JSON). Every response line carries the marker `@@FSS-PARSER@@`, so anything the native library prints to stdout is skipped. A new host
  first answers a `ping` (separates "cannot start" from "crashes while parsing").
* **One long-lived host** (started on the first parse, replaced after 500 requests) instead of one process per parse: starting a .NET
  process and loading the library costs hundreds of milliseconds per keystroke pause. A crash, hang, timeout, cancellation or garbage
  answer kills the process tree and loses only that request; the next request starts a new host. `parse_main` status 0 = valid, -1 =
  semantic errors (data still available), 1 = syntax error, 2 = preprocessor error (no data).
* **Crash handling**: the host ends at once and silently on a native crash (`CrashSilencer`: error mode, vectored handler, unhandled
  exception filter; the app also puts it into a job object), so no Windows "has stopped working" / "Exception Processing Message" box can
  appear. A text that crashed the host is not sent again; after 3 crashes in a row (different texts) the native parser is turned off for the
  session (parser.dll replaced = fresh start) and the built-in C# parser takes over (parser status "built-in"). Hosts that cannot even start
  (missing 32-bit runtime) put the parser to sleep for 15 s instead of respawning on every parse.
* The host exits when its stdin closes or its parent process disappears. Its working folder is a private temp folder (parser.dll writes
  `errors.txt` there).
* `FalloutScriptStudio.ParserHost.exe` sits next to the executable. The build copies it to the app output (`ParserHost.targets`);
  `Publish.ps1` publishes it once as a self-contained, trimmed single file shared by `FalloutScriptStudio.exe` and `FalloutScriptStudio-NET.exe`.

## Tests against the real tools

`FalloutScriptStudio.Core.Tests/Native` runs the real `parser.dll` (through the real host), `compile.exe` and `int2ssl.exe`. They are
found in `_test_files\tools` at the repository root (override: `%FSS_SSLC_DIR%`); the real mod sources are the sample sets of
`_test_files\samples` (FO2tweaksMk2 is shipped; InventoryFilterMk2 and PartyOrdersMk2 are optional; override: `%FSS_SSL_SAMPLES%`).
When something is missing the tests are reported as **skipped** (`[RealToolFact]` / `[RealToolTheory]`), not failed.
The protocol, the crash breaker, timeouts and cancellation are also tested with simulated hosts (`FakeParserHost`).

All files of the tests live in `_test_files` (see its `README.md`): the tools and samples are read-only, the tests create their scratch
folders only through `TestFolder` / `TestFiles.CreateWorkFolder` (`_test_files\work\<name>-<guid>`, git-ignored, deleted on dispose and
swept when older than one hour at the start of a run). `TestFiles.cs` and `TestFolder.cs` (in `FalloutScriptStudio.Core.Tests\Support`)
are linked into both test projects. Tests must never use `Path.GetTempPath()` or any other folder outside `_test_files`.

## Composition

* `App.xaml.cs` is a thin WPF shell; the registrations live in `Startup\AppServices.cs` and the start-up / shutdown decisions in `FalloutScriptStudio\Startup` (`StartupPlan`, `StartupCoordinator`, `ShutdownCoordinator`, tested without a WPF `Application`; `CompositionTests` builds the real container with scope and build validation). No service locator in views / view models.
* Services are registered as singletons; windows and per-window view models as transient.
* Fluent theme: `IThemeService` (light / dark / system) → `ApplicationThemeManager` + `SyntaxTheme` for the editor.
* Dialogs: `IDialogService` (Fluent message boxes, prompts, file/folder pickers).
* Single instance: `SingleInstanceService` (named pipe) forwards command-line files to the running instance.

## Patterns

* MVVM with `CommunityToolkit.Mvvm`. Code-behind only for things XAML cannot express (AvalonEdit plumbing, canvas interaction).
* Long operations are `async` with `CancellationToken` (parsing, compilation, searching).
* Colors/brushes: WPF-UI dynamic resources; syntax colors come from `Editor/Highlighting/SyntaxThemes`.
* Syntax highlighting: `Assets/Syntax/*.xshd` (AvalonEdit v2 format, named colors) + `HighlightingProvider` applies a `SyntaxTheme`
  and injects user macros.

## Problems and long operations

**One problem model.** Everything that goes wrong is a `Problem` (`FalloutScriptStudio.Problems`): a severity (Error / Warning / Info), a
source (Parse, Build, Tool, File, Settings, Message), a message (a `Str.Shell.Problem.*` key with arguments, so it follows a language change,
or the text a tool wrote), an optional file / line / column, an optional fix hint (a key) and an optional `ProblemAction` ("Open the
settings: Compiler", "Open the folder"). `ProblemFactory` creates the known ones; `IProblemService` (singleton `ProblemService`) holds the list.
A problem belongs to an *owner* (the document) and/or an *origin* (the producer, `ProblemOrigins`): it is dropped when the document is
re-parsed (source Parse), recompiled (Build and Settings), saved (a "cannot save" note) or closed (everything), and a producer replaces its
own problems when its situation changes (the native parser works again, the next build starts). The services receive the
`IProblemService` as an optional last constructor parameter.

**One list.** The Errors tab of the output panel (`OutputPanelViewModel`) shows the parser and build entries of the active script (the
legacy semantics: Error / Warning / Message, "compile all" replaces them) *and* every reported problem, grouped by source and filterable by
severity (toggles with the counts) and by source (filter menu). Click, double click or Enter on a row goes to the file and line, opening
the file when needed (the list is not replaced by the list of the file that is opened); the link of a row runs its action; "copy selected"
copies the message and its hint, "copy all" one `file(line,column): kind: message` line per row. **Ctrl+F8 / Ctrl+Shift+F8** select the next /
previous error or warning (F8 compiles, F7 is the scripts list, so the Ctrl variants of the compile key were chosen). The status bar shows
the error and warning counts and opens the tab. Search and references results keep their own closable tabs and are not problems. With no
parser entry, no build entry and no problem at all (`OutputPanelViewModel.HasNoProblems`, independent of the filters) the grid is replaced by
the "No problems" text with an icon; when only the filters hide the rows the grid stays. The grid columns have minimum widths (file 110, line
52, message 200) so that the header is never crushed.

**Failures that are reported as problems:** missing or unstartable compile.exe / preprocessor / usercomp.bat / int2ssl.exe (`ToolFailure`
of `CompilationResult` / `DecompilationResult`, the raw log line is then not duplicated in the list), a compilation that fails without an
error position, the output folder not set, parser.dll missing (note) or broken / switched off after crashes (warning), a parse that threw,
files that cannot be opened, saved, reloaded or extracted from an archive, a file read with the fallback code page (note), includes and
message files that are not found, damaged / unreadable / unsaveable settings files (`ISettingsService.Problems` / `ProblemRaised`), an
external editor that does not start, a background operation that failed (`GuardAsync`). Message boxes stay where the user must answer.

**Cancellable operations.** A build command, a mass compilation and the decompilation of a compiled script are each one `IOperation` of the
`IOperationTracker` (only one runs at a time; the other build commands are disabled meanwhile and refused with a status message). The
status bar shows what runs ("Compiling a.ssl (3/12)", a progress bar) and a Cancel button; **Esc in the output panel**, **Ctrl+Break** and
the Compile menu cancel it too. The token goes down to `ProcessRunner`, which kills the whole process tree (the tool, the `cmd.exe` of a
batch file and what it started; a job object is the safety net) and returns only when the processes are gone. `ScriptCompiler` then
restores the previous `.int` (or deletes the half-written one), deletes the preprocessed intermediate files and the `mcpp.err` / `wcc.err`
log, and `BatchCompileService` cancels every compilation in flight. The operation is always ended in a `finally` (a `using`), so the UI
never stays busy after a cancel or an error. Advanced search keeps its own Cancel button and token.

## Incremental builds and compile profiles

**What is stale.** `FalloutScriptStudio.Core.Building` decides, for each script, whether its compiled file is up to date. `IncludeScanner` (pure) finds the `#include` directives of a text (comments and string literals skipped, `#if` nesting tracked); `IncludeGraph` / `IncludeScan` follow them through the include resolver (`IncludeResolver`: the folder of the including file, the headers folder when `IncludeSearch` allows it, the program folder), keep the directives of a file as long as its stamp (size + last write time, `FileStamp`) does not change, and return a `DependencySet`: the files that exist (cycles are followed once, paths compare ignoring case), the missing includes inside `#if` blocks (watched: the script is stale when such a file appears), and the includes that cannot be resolved (missing file, `#include MACRO`, unreadable file: the script is then never trusted). `BuildFingerprint` is a SHA-256 of the options that reach the command line (optimization, short-circuit, backward compatibility, debug information, preprocessor kind and definition, the headers folder when includes are searched) and another one of the size and time of `compile.exe` and of the preprocessor in use. `BuildCache` is `fss-build.json`: for each script and output file one `BuildRecord` (fingerprints, whether short-circuit was in force, the stamps of the source, of the compiled file and of every dependency, a path table keeps the file small), written atomically; a missing, damaged, wrong-version or locked file gives an empty cache (`BuildCacheStatus`), never an exception, and a file changed by another program is read again. Its location is `BuildCache.GetFilePath`: the project folder, otherwise the settings folder.

**The rule.** `IncrementalBuildService.Plan` returns a `BuildDecision` per script: up to date only when the output exists, a record exists for that script *and* output file, the option and tool fingerprints and the short-circuit flag match, the stamp of the compiled file is the one recorded (so a file rebuilt or replaced by anything else is stale), the source and every dependency have exactly the recorded stamps, and the set of files the includes resolve to is the recorded one. Equality of stamps, not "newer than", is what counts: a header restored from a backup with an older time, or a time stamp in the future, is handled (a future stamp is not stale for ever, any change is). Anything else gives a `StaleReason` (not built, options or compiler changed, source or dependency changed, output deleted or replaced, unresolved include, user batch file: never cached, output folder not set, forced). `BuildTicket` (from `Begin`) takes the stamps *before* the compiler runs, so a file saved during the compilation makes the result stale at the next check; `Succeeded()` records the build, `Failed()` forgets any record (a failed compilation is never up to date), a cancelled compilation reports nothing and `ScriptCompiler` has restored the previous `.int`, which still matches its record. Checking 5 000 scripts with a warm cache takes about 0.1 s.

**Who uses it.** `BatchCompileService` (Mass Compile): with `BatchCompileOptions.BuildCacheFile` every success is recorded and the cache saved at most every 5 s and at the end (also after a cancel, so an interrupted run is resumed by the next one); with `OnlyChanged` it plans first and compiles only the stale scripts (`BatchCompileResult.UpToDate`, `UpToDateScripts`; `BatchCompileProgress.Total` counts the scripts to compile and `UpToDate` the skipped ones, and an initial progress with `Completed = 0` announces them). `BuildCoordinator`: *Build Changed* plans the open scripts (a script with unsaved changes or without a file is always stale), *Compile All Open* and every single compile (F8) record their builds too, *Rebuild All* is a mass compile with `rebuildAll`. The operation is the usual `IOperation` (`OperationInfo.UpToDate`: "Compiling x (3/12), 9 up to date"), the status ends with "12 compiled, 9 up to date, 1 failed", the build log says how many scripts were skipped (their names with `CompilerSettings.ListUpToDateScripts`). The setting "only changed scripts" of the mass compile is `CompilerSettings.MassCompileOnlyChanged` (menu toggle, default on). The cache is not used for round trips, preprocessing, or when the user batch file compiles. `fss-build.json` is a machine local file (time stamps): a mod that is kept in version control should list it in its ignore file.

**Compile profiles.** `CompileProfile` is a named set of optional values (optimization, short-circuit, backward compatibility, debug information, preprocessor definition; `null` = not set, an empty definition = none). The global ones are `CompilerSettings.Profiles` ("Debug" and "Release" for a new installation, an older settings file gets them too) and `ActiveProfile`; a project adds `ProjectSettings.CompileProfiles` (a profile of the same name replaces the global one) and may choose its own `ActiveCompileProfile` (an empty text selects none), both listed by `GetOverriddenOptions`; unknown properties of a profile are kept like those of the file. `EffectiveSettings` merges the lists (`CompileProfiles`), resolves the active one (`ActiveCompileProfile`) and applies it in `Combine`, after the project options: global < project < profile, the settings are never modified and `Settings` is still the global instance when there is no project and no profile. Because the profile only changes the effective `CompilerOptions`, the fingerprint changes with it and the scripts become stale by themselves. UI: a toolbar combo (`MainViewModel.SelectedCompileProfile`: writes the project file when the project chooses, the global setting otherwise; the definition combo is disabled while the profile sets the definition), `CompileProfileEditorViewModel` / `CompileProfilesEditor` (add, rename, delete, "inherit / override" per option) in the Compiler page of the Settings window and in the project settings window (with the active profile card).

## Projects: mod folders and `fss-project.json`

A *project* is a folder (a mod) that may hold a `fss-project.json`. It overrides, for that mod only, the global options that differ between
mods; with no project open nothing changes.

* **Active project = `Paths.SolutionFolder`.** The folder of the global settings (the one the project explorer lists) is the project folder, so
  the explorer, the older code paths and a legacy `SolutionFolder` keep working: an old solution folder is simply a *project folder without a
  settings file*. `IProjectService` (`ProjectService`, Core) follows that setting whoever changes it (File > Open Project, the explorer, the
  command line), reads the project file, keeps the recent projects (`RecentFiles.Projects`, newest first, 10 at most, in `recent.json`) and
  raises `ProjectChanged`. A folder passed on the command line is opened as a project.
* **`fss-project.json`** (`ProjectSettings`, `ProjectSettingsFile`): versioned, written atomically (`AtomicFile`), unknown properties are
  kept when it is written again, comments and trailing commas are tolerated. A damaged file is copied to `.corrupt` and the project inherits
  everything until the user creates a new one; a file that cannot be read is never overwritten (saving is refused). A `null` value means
  "inherit the global setting"; for the paths and the selected definition an empty text is an override meaning "not set". Paths are
  stored relative to the project folder with forward slashes (portable between machines) and resolved when loaded.
  Overridable: headers folder, `scripts.h`, output folder, "compile next to the source", "search includes", preprocessor, selected
  definition, optimization, short-circuit, backward compatibility, warnings, debug information, message folders (replace the global list),
  the location of `scripts.lst`, a display name, the compile profiles the project adds and the active one (see "Incremental builds and compile profiles"); the definitions of the project are added to the global ones in the toolbar list.
* **One place combines the two: `ISettingsService.Effective`** (`EffectiveSettings`). Its `Settings` is the global `AppSettings` itself when
  the project overrides nothing, otherwise a copy with the overrides applied (the global settings are never modified). Every consumer of the
  compiler, header, include, definition and message folder options reads them from there: `CompilerOptions`, `ParserOptionsFactory`,
  `IncludeResolver`, `MessageFileOptions`, the register-script dialog (`scripts.lst`), the batch compiler, the toolbar list of definitions.
  Options that are not per project (editor, decompiler, user batch file, window layout...) stay on `ISettingsService.Settings`; the
  Settings window edits the global settings only. `SettingsService.SetActiveProject` swaps the folder and the overrides as one unit and raises
  `SettingsChanged`.
* **Applying a change.** `MainViewModel` reacts to `ProjectChanged` (a project opened or closed, the settings saved) like it does after the
  Settings window: the toolbar definitions, the global macros of the headers folder and every open script are refreshed and parsed again.
* **Detection.** `ProjectLocator` looks for `fss-project.json` in the folder of an opened script and the four folders above it (five levels,
  the nearest wins). When it belongs to a project other than the active one, an *information* problem with a "Switch to this project" link is
  reported (never a dialog), once per project and session.
* **Watching the project file.** `ProjectService` owns a `ProjectFileWatcher` (Core) for the folder of the active project; it is created when
  a project is opened, replaced when the project changes, and disposed when the project is closed or the container is disposed (`IDisposable`).
  A file system event only starts a quiet period (`ProjectFileWatchOptions.Debounce`, 300 ms); a slow safety net compares size and time every
  2 s in case the file system reports nothing (network folders). When the file is examined, a locked file is read again with a bounded
  doubling backoff, a missing file or an invalid content is looked at again a few times (`SettleAttempts`) so that an editor that saves through a
  temporary file and a rename, deletes and recreates the file, or is still writing, is one change and a half-written file is never applied.
  The outcome is a `ProjectFileChange`: *Modified* (valid content: applied through the same path as `Reload()`, which raises
  `ProjectChanged`, so the effective settings, the toolbar definitions, the global macros and every open script follow like after a project
  switch), *Invalid* (the last valid settings stay in effect; `IProjectService.FileChangedOnDisk` carries the parse error with its line and
  column) or *Deleted* (the project becomes a folder without settings). The editor's own saves are recognised by the SHA-256 of the content:
  `SaveSettings` acknowledges the bytes before it writes, `Read` acknowledges what it read, so only a content that differs from what the editor
  holds is a change (no reload loop). The change is posted to the synchronization context the service was created on (the UI thread).
  `MainViewModel` turns `FileChangedOnDisk` into a status text ("Project settings reloaded") or, for an invalid content, a *Warning*
  problem (`ProblemOrigins.ProjectFile`) with the line and column and an "Open the file" link (the editor opens `.json` files as plain text);
  it is cleared by the next valid content or when the project changes. A file saved with a byte order mark (Notepad, PowerShell) or as UTF-16 is read.
* **Which options a project overrides.** `ProjectSettings.GetOverriddenOptions()` / `EffectiveSettings.GetOverriddenOptions()` list the option
  identifiers (`ProjectOptions`, the property names of `ProjectSettings`) that have a value in the file. The Settings window uses them: a
  `SettingCard` carries `OptionId`, the implicit style binds `IsOverridden` to `SettingsViewModel.OverriddenOptions`, and the template shows
  "Overridden by project X" with a link ("Edit project setting" opens the project settings window on that option, `ProjectSettingsViewModel.FocusOptionId`),
  dims the control and sets a tool tip; the global value stays editable and is never replaced by the project value.
* **Open documents per project.** `RecentFiles.ProjectSessions` (in `recent.json`, written with the same atomic and merged saves as the other
  settings) keeps for at most 20 projects (the oldest is dropped) the open documents of the project folder, relative with forward slashes, and
  the active one (`ProjectSession`); the caret line and the folds stay in `positions.json` / `folding.json` and come back when a document is
  opened. `ProjectSessionService` (Workspace) captures the list when the project is left (`ProjectChanged` with another folder, Close Project) and
  when the program ends (`CanCloseAsync`, before the documents are closed); documents outside the project folder and untitled ones are not
  remembered. When a project is opened (menu, recent list, command line folder, or at start-up without files on the command line) and the editor
  option "Restore the open files of a project" (`EditorSettings.RestoreProjectDocuments`, default on) is on, the remembered files that still
  exist are opened in the background at once when nothing is open, with the remembered active one in front; when documents are open already a
  *Information* problem with a "Restore open files" link is reported instead (`ProblemOrigins.ProjectSession`). Missing files are skipped and logged.
  With the option off, or without a project, nothing is offered and nothing changes.
* **UI.** File menu: Open Project, Recent Projects, Create Project Settings, Close Project, Show Project Folder in Explorer; Options menu and
  a click on the project name in the status bar: *Project settings* (`ProjectSettingsWindow` / `ProjectSettingsViewModel`). For each option
  the window offers "Inherit global" / "Override" (`OverrideModeBox`, `ProjectOption<T>`) and the value; the result is saved to
  `fss-project.json`, never to the global files. The project name is shown in the status bar and the window title. The window also has
  "Reload from file" (reads the file again, discarding what was typed and not saved) and "Open fss-project.json" (closes the window and opens the file in the editor).

## Project index and code intelligence

**One index of the whole project.** `IProjectSymbolIndex` (`FalloutScriptStudio.Core.Indexing`, `ProjectSymbolIndex`) holds the procedures, `#define` macros (with their parameters) and script level variables (`variable`, `import variable`, `export variable`) of every `.ssl` and `.h` file below its *roots* (`ProjectIndexRoots`): the project folder, or the folders of the open scripts, plus the headers folder of `ISettingsService.Effective`. It reuses the editor's own scanners (`InternalParser` for procedures, `MacroCollector` for macros) and the token based `SslScriptModel` for variables, keeps only symbols (never the text of a file: about 12 MB for 54 000 symbols in 4 250 files, hard limit 300 000 symbols for the x86 address space) and skips `.int`, binary files and files above 5 MB; files are read with the code page of `Editor.FileEncoding` (BOM, then strict UTF-8, then that code page). A run lists the files, compares size and time stamp with the previous snapshot (a file written less than 2 s before it was read is read again) and reads only what changed, on at most four pool threads, with cancellation between files; the snapshot is replaced as a whole, so a query never sees half an update. `Search` ranks exact > prefix > start of a word > substring > letters in order (`SymbolMatcher`), several words must all match (the next ones may match the file name), `Find` is a dictionary lookup, `FindOccurrencesAsync` scans the files that can *see* a definition (the files that include its file, `GetFilesSeeing`; every file for `import`/`export` names) with the open documents' texts instead of the disk.

**Who keeps it up to date.** `ProjectSymbolService` (`Workspace`) computes the roots, runs the index in the background (debounced) on start, project change, document open / close (only when the roots change), settings change, save / reload (`UpdateFileAsync`) and window activation, and writes "Indexing 1200/5000" / "Indexed N symbols in M files" in the status bar for runs of 10 files and more (it does not use `IOperationTracker`, which would block the build commands). `CodeIntelligenceOperations` implements what the user asks: `NavigateAsync` (definition / declaration / references of a name the document does not resolve, a list `SymbolPickerWindow` in *Choose* mode when there are several candidates, ordered by `SymbolCloseness`), the *Go to Symbol* list (*Search* mode), project wide references, *Delete Unused Procedure*, *Find Unused Variables* and *Extract Procedure*. The editor asks through `IWorkspace` (default interface members, so fakes keep compiling); `NavigationController` keeps the old behaviour whenever the document or its includes resolve the symbol.

**Semantic diagnostics (`ScriptDiagnostics`, `Core.Analysis`).** The compiler only reports an unknown name or a wrong number of arguments when the script is compiled; `ScriptDiagnostics.Analyze` finds them while the user types. It is pure: it takes the tokens (`SslTokenizer`) and a `ScriptEnvironment` (the macros of the parse result, the procedures and variables of the included headers, the descriptions of the functions) and returns `ScriptDiagnostic`s (code `SSLnnnn`, severity, localization key + arguments, range, optional `ScriptQuickFix`). Three passes: the preprocessor lines (`#define`, `#include`, `#if` groups: only the first branch of a group is analysed, the names of the others are remembered so they are never reported missing), an outline of the declarations and of the `begin` / `end` structure, and a pass over the bodies that resolves every name in the order of the compiler (macro, local, global, procedure, built-in, then why it was not found). `SSL1xxx` are rules sslc enforces (found by compiling small scripts with the real compiler: a procedure must be defined or forward declared before its use because sslc reads the file once; the scope of a local is the whole procedure, not the block; a forward declaration fixes the argument count of the calls before the definition and a definition with default values may not have one; a statement cannot start with a procedure name, it needs `call`; a standard handler such as `start` that is only declared fails even when unused...). `SSL2xxx` compare a call with `opcodes.txt` / `functions.ini` (`FunctionSignatureCatalog`: `type name`, `[optional]`, `...`, a function without parameters is written without parentheses; a name in both files is accepted if either signature accepts the call) and are never more than warnings. The rules are conservative by design: an unreadable header (`ScriptEnvironment.IsComplete`), a macro that declares names or stands for `begin` / `then` / several arguments, a top-level use of an unknown macro or a branch of an `#if` lower or silence them, so a script the compiler accepts is never reported with an error. `ScriptBuiltins` is the list of names sslc knows without any header (it was produced by asking the compiler; `opcodes.txt` misses some, for example `false` and `bwand`). `ScriptEnvironmentBuilder` follows the `#include`s with `IncludeResolver` and reads every header once through the thread safe `IncludeSymbolCache` (size and time stamp; a file saved less than two seconds ago is read again); a header it cannot find can be located by name in the project index. The tests (`ScriptDiagnosticCases` table) run every case against the real `compile.exe` (`RealScriptDiagnosticsTests`: the compiler verdict must be the table's, and the analysis must flag the script exactly when it is rejected), the sample scripts and a generated valid script of 20 000 lines must give no error, `RealFunctionCatalogTests` compares the argument checks with the compiler for the functions of the catalog, and a performance guard keeps 20 000 lines under 100 ms. In the application `LiveDiagnosticsService` (`Workspace`) follows `IWorkspace.DocumentParsed`: a short pause, then the analysis runs on a pool thread on a snapshot (text, `ProgramInfo` macros, include resolver, unsaved texts of open headers, function descriptions re-read when their files change); a newer parse cancels it and a result for a text edited meanwhile is dropped (`DocumentViewModel.LiveDiagnosticsVersion`). The findings go to `DocumentViewModel.LiveDiagnostics` (`DiagnosticsController` underlines them with the severity colors, tool tip = message + quick fix + gesture; they are not drawn for another text version) and to the problem list (`ProblemFactory.ScriptDiagnostic`, source Parse, origin `LiveDiagnostics`, hint, a `ProblemActionKind.ApplyQuickFix` link); an error the native parser already reports on the same line is not repeated unless it brings a fix. The setting `EditorSettings.LiveDiagnostics` (`LiveDiagnosticsLevel`: Off, ErrorsOnly, ErrorsAndWarnings; default ErrorsAndWarnings) is global: `EffectiveSettings` only combines the `Paths` and `Compiler` sections, the editor section has no per-project override. **Quick fix**: the command `EditorCommand.QuickFix` (Ctrl+., Code menu, context menu) and the link of a problem call `IWorkspace.ApplyQuickFixAtAsync` / `ApplyQuickFixAsync`, which analyse the current text again (`LiveDiagnosticsService.AnalyzeNow`), build the edits with `ScriptQuickFixes.CreateEdits` for that text and apply them as one undo group, then parse again.

**Text refactorings are pure Core.** `SslTokenizer` / `SslScriptModel` (`Core.Analysis`) give tokens (comments and strings skipped, preprocessor lines marked), procedures with bodies and every declared variable; `UnusedVariableFinder` (never used / assigned but never read; macro bodies and the words of included macros count as uses; a declaration is removable when its initialiser calls nothing), `VariableDeclarationEditor`, `SymbolOccurrenceScanner`, `UnusedProcedureRemover` (plan with leading comment block and forward declaration; engine handlers, `*_p_proc` and the names of `prochandlers.ini` are never removed) and `ProcedureExtractor` (checks complete statements, balanced `begin`/`end`, no `return`, `break` / `continue` only for loops inside the block; parameters in order of first use, locals only used inside move, one changed and later read variable is returned) return `TextEdit`s that the workspace applies as one undo group (`TextDocumentEdits.ApplyEdits`). The `ShowUnusedVariables` option (global only) makes `DiagnosticsController` draw `MarkerSeverity.Unused` marks after each parse (about 18 ms on 20 000 lines).

## Script / message file consistency and dialogue preview from a node

**Pure Core checker.** `ScriptMessageConsistency` (`FalloutScriptStudio.Core.Dialogue`) compares a script with its `.msg` file. `ScriptMessageScanner` finds every message number the script uses: it masks comments, string literals and preprocessor lines (`ScriptMessageMasker`, offsets are kept), then reads every call `name(args)` whose name shows a message, even across several lines (`MessageCallArguments`). `MessageCallResolver` knows those names: the dialogue rules (built in and the user's `DialogFunc.cfg`: `NMessage`, `Reply`, `NOption`, `gsay_reply`, `giq_option`...), `message_str`, the function-like macros of the script and its headers that expand to one of them (`#define mstr(x) message_str(NAME, x)`, `#define floater(x) float_msg(self_obj, mstr(x), 0)`, followed through several levels, the message argument being a parameter or a parameter plus a number) and, like the legacy parser, any other macro whose name contains `Reply`, `Message` or `Option`. `MessageExpressionEvaluator` works out the number: decimal and hexadecimal literals, object-like macros, macros with arguments, `+ - * / %`, parentheses and `random(a, b)` (a range); a variable or an unknown name makes the use *unresolved*. The message file of a use is the script itself when the file argument is the script number (`ProgramInfo.ScriptNameId`, the `NAME` macro) or the `NAME` macro whose header is missing; other `scripts.lst` numbers are kept apart (`ScriptMessageScan.OtherFileNumbers`) and checked against the files the caller loads (`IMessageFileService.LocateById`).

The report (`ScriptMessageReport`) lists, in this order, the numbers used but absent (error, place in the script, once per use), the duplicate numbers of the file (error, second line), the used messages with an empty text (warning), the used dialogue messages without a female variant (`n + 1000`, information; only when the script mentions `female` / `gender`, or the file has a variant of a used message that the script does not use itself), and the unused messages (information). The unused messages are only listed when every number of the script could be worked out and at least one use was found; otherwise one *unresolved uses* / *no use found* note replaces them, so a variable never makes a message look unused. A script that uses messages and has no message file gives one `MessageFileMissing` finding. Comment lines and unrecognised lines of the file are not messages; lines are physical lines (a multi-line message counts its lines).

**Application side.** `MessageConsistencyService` (`Workspace`) is attached to `WorkspaceService`: `IWorkspaceManager.CheckMessagesAsync` runs it (command *Check Messages*, Dialogue menu, Ctrl+Shift+M), and `IWorkspaceManager.DocumentSaved` (raised after a document was written, and after the Message Editor saved the file of a script) schedules it when the setting `Messages.CheckMessagesOnSave` (default on) is on, the script has a message file association (or the saved document is the message file of an open script): a quiet period of 800 ms (a newer save, a manual check or closing the script cancels the pending one with its `CancellationToken`), the scan and the check run on a pool thread, the message file is read from its open tab when there is one (unsaved edits count). The result replaces the problems of that script with `Origin = ProblemOrigins.MessageConsistency` (`ProblemFactory.ScriptMessage`, source Message, keys `Str.Shell.Problem.Msg*`); a click goes to the script line for a missing number and to the line of the message file for the others; at most 500 unused-message and 500 female-variant notes are listed. The lookups of `MessageAssociationService` keep these problems (they only remove their own message file problems). Two links: `ProblemActionKind.AddMissingMessages` appends `{n}{}{}` for the missing numbers (`IMessageFileService.AppendMessagesAsync`: existing lines untouched, new lines after the last non-blank line, atomic write; an open tab without unsaved changes is reloaded, a tab with unsaved changes receives the lines instead and the file is not written; a Message Editor window shows its own "file changed" banner) and `ProblemActionKind.CreateMessageFile` (finds or creates the file with the usual confirmation and associates it); both check the script again.

**Preview Dialogue From This Node.** `DialogueNodeRule.IsNode` is the one rule for dialogue nodes (name contains `node`, or `talk_p_proc`): the parser, *Edit node code* and the preview use it. `DialoguePreview.StartAsync(..., startNode)` starts at a node instead of the caret / `talk_p_proc` (an unknown name is ignored) and `GoToNodeAsync` moves an open preview to a node by adding it to the history, so Back works. `IScriptToolService.ShowDialoguePreviewAsync(script, DialoguePreviewOpenOptions { StartAtNode })` opens the window or, when one is already open for the script, calls `DialoguePreviewViewModel.ShowNodeAsync` (it first reads the changes of the script) and brings the window to the front. The entry points all end in `IWorkspace.PreviewDialogueFromNodeAsync` (which needs a saved script with a message file, like the Dialogue menu command): the *Procedures* panel context menu (`ProceduresPanelViewModel.PreviewDialogueCommand`, enabled by `ProcedureNodeViewModel.CanPreviewDialogue`), the editor command `EditorCommand.PreviewDialogueFromNode` (Ctrl+Shift+P, context menu item shown only while the caret is inside a node procedure, Dialogue menu) and the flowchart node context menu (`FlowchartViewModel.PreviewNodeCommand`).

## Command palette

**One registry of the commands.** `CommandCatalog` (`FalloutScriptStudio\Commands`) is the table of the menu items of `MainWindow.xaml`: for each one the localization keys of the menus above it and of its own header, the command of `MainViewModel` it runs (a property path such as `Output.NextProblemCommand`, resolved by reflection), the command parameter (an `EditorCommand`, an `AppTheme`) and when it is enabled (`CommandRequirement`: the same conditions as the `DocumentMenuItemStyle` / `ScriptMenuItemStyle` / `ParsableMenuItemStyle` and the `IsEnabled` bindings). Check items are entries that flip a Boolean property of the view model. `CommandCatalog.Create(viewModel)` binds the table and adds what has no menu item or changes at run time: every command of `EditorCommands.All` that no menu item runs (under "Editor"), the templates, the recent files and projects, the languages, the compile profiles and the preprocessor definitions. **The table cannot drift from the window**: `CommandCatalogTests` read `MainWindow.xaml` statically and fail when a menu item with a command or a check box is missing from the table, when the table lists one that does not exist, when the menu path, the header key or the enabled condition differ, and when a key binding runs a command that the palette does not list. The names are never stored: a `CommandText` is a localization key (or a literal such as a file name) read through `Loc` when asked, the menu path comes from the plain texts `Str.Shell.Palette.Menu.*` (the headers of the menu bar carry an access key marker, which code must not read; a test checks the two sets of texts agree in every language), and `MenuText.Clean` removes the ellipsis and any marker. The id of an entry (`SaveCommand`, `EditCommand:FormatDocument`, `toggle:ShowLog`, `language:fr`) is what the list of recent commands remembers.

**The window.** `MainViewModel.ShowCommandPaletteCommand` (F1, View menu) asks `IToolWindowService.PickCommandAsync` for a `CommandPaletteRequest` (entries, recent ids, `ICommandGestureSource`); `CommandPaletteViewModel` / `CommandPaletteWindow` list the entries (`CommandPaletteItem`: name, menu path, shortcut, state, reason) and filter them with `FuzzyMatcher` (Core, pure: exact > prefix > start of a word > substring > letters in order; case and accents ignored; several words must all match; `GetTier` gives the kind of match). Without a filter the recent commands come first (newest first); with a filter the kind of match decides, then recent before not recent, then the closer match, then the order of the menus. A command that cannot run (`CommandAvailability`: needs a document, a script, a project, nothing to undo...; or its `ICommand.CanExecute` is false) stays in the list, dimmed, with the reason, and cannot be chosen. Up / Down / Page Up / Page Down move in the list while the filter box keeps the focus, Enter runs, Esc closes; the status line is a live region ("12 command(s)", and why the selected command is unavailable). The shortcut of a row comes from the menu and the key bindings of the real window (`WindowGestureSource`, set on `MainViewModel.GestureSource` by `MainWindow`) or, for an editor command, from `EditorCommands`.

**Running.** The window closes first; `MainViewModel.RunPaletteCommandAsync` then checks the entry again (`CanRun`), remembers its id (`RecentFiles.Commands`, the last 10, in `recent.json`, saved atomically with the other settings), gives the focus back to the editor and runs the same `ICommand` as the menu (awaited when it is async, under `GuardAsync`); an editor command goes through `MainViewModel.Edit` and `IEditorSurface.Execute` of the active editor.

## Replace in Files

**Three steps, nothing changes before the second.** `ReplaceInFilesService` (`Services\ScriptTools\Replace`) runs them for the advanced search window (`AdvancedSearchViewModel.ReplaceInFilesCommand`, scopes: current script, open scripts, folder with masks and sub folders) and for the Edit menu (`MainViewModel.ReplaceInFilesCommand`, Ctrl+Shift+H: opens the search window with the folder scope):

1. **Plan** (`ReplaceInFilesPlanner`, worker thread, cancellable, progress like the search). It uses the matcher of the search (`SearchMatcher`: case, whole word, regular expression with its time limit, line by line) and produces a `ReplacePlan`: per file a `ReplaceFilePlan` with a SHA-256 of what was read and the `ReplaceMatch`es (offset in the raw text, line, column, matched text, expanded replacement, the line before and after the match). The files are read one at a time and only the matches are kept, never a text (5 000 files: managed memory unchanged, peak working set 87 MB); at most 50 000 replacements are listed (`Truncated` tells the preview, the rest is found by running again); binary files and files above 32 MB are ignored; a read-only file with matches and a file that is locked are not planned and are reported (`ReplaceSkip`). An open document is planned from its text (unsaved edits included) with the document as owner; a regular expression that exceeds its time limit throws `RegexMatchTimeoutException`, shown as an error of the window.
2. **Preview** (`IReplacePreviewPresenter`, `ReplacePreviewWindow` / `ReplacePreviewViewModel` / `ReplaceNodeViewModel`): a tree of the files with their replacements, each replacement as the line before (`-`, the matched part struck through) and after (`+`, the replacement in bold), a check box per file (tri-state, ticking it ticks its replacements) and per replacement, all ticked at first, buttons Select All / Deselect All / Expand All / Collapse All, a summary ("42 replacements in 7 files (of 60 found)", a live region), the files left out in an expander, a warning when the list is truncated, **Replace Selected** (default button, Ctrl+Enter) and Cancel. Space ticks the selected row.
3. **Apply** (`ReplaceInFilesApplier`, on the UI thread with asynchronous file access): every file is read again and must have the hash it had in the plan (an open document the same text, every match the same characters at its offset), otherwise it is left alone (`ReplaceFailureReason.Changed`), like `SymbolRenameService` does for a rename. An open document is edited with `TextDocumentEdits.ApplyEdits` (one undo group; it stays modified and unsaved; it is parsed again); a document closed meanwhile is reported (`Closed`). Any other file is decoded with `DocumentTextCodec` (BOM, UTF-8, UTF-16, else the code page of the settings), edited on the raw text (line breaks untouched), encoded again with the same encoding and byte order mark through an encoder that refuses what it cannot hold (`NotEncodable`, never `?`) and written by `IDocumentFileWriter` (`AtomicDocumentFileWriter`: temporary file, flush, move; a read-only, locked or failing file keeps its content and no temporary file stays behind). A file that cannot be changed is reported and does not stop the others; cancelling stops between two files and keeps what was done.

**Reports and undo.** The files left out or left unchanged become `Warning` problems (`ProblemFactory.ReplaceFileSkipped`, origin `ProblemOrigins.ReplaceInFiles`, replaced by the next run, with the file link) and the status line says "N replacement(s) in M file(s)" and how many files were not changed. The service keeps a `ReplaceUndoRecord` of the last run in memory: per changed file the SHA-256 of the result and the reverse edits (offset in the new text, length, old text: a few strings per replacement, never the content of a file). **Edit > Undo Last Replace in Files** (`IScriptToolService.UndoReplaceInFilesAsync`) restores every file that still has that hash (open documents: the same text, restored as one undo step) and reports the others as problems ("modified since").

## Code formatting

**Options.** `FalloutScriptStudio.Core.Formatting.FormatOptions` is the whole style as an immutable value (indentation as tabs or spaces and width, `Reindent`, `ContinuationIndent`, `AlignContinuationToBracket`, `Begin` / `ElseBegin` / `Else` placement, `OperatorSpacing` / `AssignmentSpacing` / `CommaSpacing` (`Keep`, `Add`, `Remove`), `ParenthesisSpacing`, `FormatPreprocessorLines`, `BlankLinesBetweenProcedures` (0 to 3 or `KeepBlankLines`), `MaxConsecutiveBlankLines`, `TrimTrailingWhitespace`, `EnsureFinalNewline`, `AlignDefines`, `MaxLineLength`); `Normalize()` brings every value into its range. Core never reads the settings: the application builds it. `FormatSettings` is the stored form (`EditorSettings.Formatting`, a project's `ProjectSettings.Formatting`, plus `FormatOnSave`); its `IndentStyle.FromEditor` and `IndentSize = 0` take `TabsToSpaces` / `TabSize` from the editor settings, `ToOptions(EditorSettings)` makes the options, `Normalize()` repairs a hand-edited file and unknown properties of `fss-project.json` are kept like the others. `EffectiveSettings.Formatting` is the style in force (project over global, a project that has none leaves the global one) and `ToFormatOptions()` the options; `GetOverriddenOptions` lists `Formatting` (`ProjectOptions.Formatting`) like any other overridden option. **The default options reproduce the original formatter byte for byte**: the legacy algorithm is kept as a test oracle (`FalloutScriptStudio.Core.Tests\Formatting\LegacyCodeFormatter`) and compared with `CodeFormatter.Format` on the samples and on generated operator soup.

**Passes.** `CodeFormatter` (`TextTools`, unchanged API plus overloads taking `FormatOptions`) runs `FormatPipeline`: `SpacingPass` (operators, `:=`, commas; the lexer `FormatLexer` knows strings, comments, character-like tokens, `#include` lines and the macro lines that must stay verbatim, so nothing inside them is touched), then, only when a structural option is on (`FormatOptions.IsStructural`), `ParenthesisPass`, `PlacementPass` (the position of `begin` and `else`, using `LayoutAnalyzer` / `LayoutInfo` which follow `begin` / `end` nesting even in a text that is cut in the middle of a construct), `IndentPass`, `WrapPass` (argument lists longer than `MaxLineLength` are broken at their commas, continuation lines indented), `BlankLinePass`, `DefineAlignmentPass`, `WhitespacePass` (trailing white space, final line break). The line breaks of the text (CRLF / LF) are kept, formatting twice gives the same text (the pipeline is idempotent: every option set is tested on the sample scripts, on texts cut at every construct and on generated scripts of 5 000 and 20 000 lines), and only white space changes (`FormatSamples.Signature` compares the tokens). `LineDiff` / `UnifiedDiff` compute the lines that change (so Format Document edits only those lines: one undo step, the caret and folds stay where they are) and the before / after text of the preview. Formatting a selection with a structural option works on the whole document (the indentation depends on the blocks around it) and applies only the edits inside the selected lines. `FormatPreviewSample` is the fixed script shown by the options page.

**The compiler decides.** `FormatCompilerTests` (`[RealToolTheory]`) compiles every script of `_test_files\samples\FO2tweaksMk2\source` before and after formatting with several option sets and requires the same compiled file (the `.int` holds no time stamp, so the bytes are compared; when a tool is missing the tests are skipped).

**Application side.** `FormattingEditorViewModel` / `FormattingOptionsEditor` (one user control, used by the Settings window and, inside an enabled-only-when-overridden card, by the project settings window; `SettingsViewModel.FormattingEditor`, `ProjectSettingsViewModel.FormattingMode` / `FormattingEditor` follow the way the compile profiles were added) show the options as choices and numbers, with the preview of `FormatPreviewSample` formatted live and a *Defaults* button. The editor commands (`EditorCommandHandler.FormatDocument` / `FormatSelection`), the formatting after `;` (`InputController`), *Auto Formatting Code* on open and *Format on save* (`WorkspaceService.Saving.FormatBeforeSave`, scripts and headers only, applied to the document as one undo step so the editor shows what was written) all take the options from `ScriptEditorServices.GetFormatOptions()` / `ISettingsService.Effective`. **Format Project** (`Workspace\Formatting`): `ProjectFormatService.PreviewAsync` reads the files of the scope one at a time on up to four threads (project folder with masks, `*.ssl;*.h` by default, files above `MaxFileSize` ignored; or the open scripts and headers, from their text), formats them and keeps only a `FormatFileChange` (path, number of changed lines, SHA-256 of what was read, the open document) so 5 000 files cost a few megabytes; `GetDiffAsync` builds the before / after text of one file; `ApplyAsync` applies the checked changes with the rules of Replace in Files: the file (or the text of the open document) must still have the hash of the preview, otherwise it is skipped; an open document is edited with `ApplyEdits` (one undo group, it stays unsaved); other files are decoded with `DocumentTextCodec`, formatted again, encoded with the same encoding, byte order mark and line breaks and written by `IDocumentFileWriter` (temporary file and move); a read-only, locked, unreadable or changed file becomes a `Warning` problem (`ProblemFactory.FormatReadOnly` / `FormatFileChanged` / `FormatFailed`, origin `ProblemOrigins.FormatProject`) and does not stop the others; both steps report through `IOperationTracker` (`OperationKind.FormatProject`) and a `CancellationToken` (cancelling stops between two files and keeps what was done). `FormatProjectViewModel` / `FormatProjectWindow` list the files with a check box and the count of changed lines, show the selected file's before / after text in a read-only view, and are tested without a window.

## Snippets

**Model and files.** A `Snippet` has a trigger, a description and a body; `SnippetDefinition` is its stored form (trigger, description, body as a text or a list of lines, `Enabled`; unknown properties are kept). `SnippetFile` (`snippets.json` in the settings folder for the user, `fss-snippets.json` in the project folder) has a version; `SnippetFileStore` reads and writes it with the safety rules of the other settings files: comments and trailing commas are tolerated, a write goes through `AtomicFile`, a damaged file is copied to `.corrupt` and counts as empty until the user saves, a file that cannot be read (`SnippetFileStatus.Unreadable`) is never overwritten. `SnippetService` (`ISnippetService`) reads the two files again when their size or time changes, and `SnippetCatalog.Merge` combines built-in, user and project snippets per trigger (the latest source wins, ignoring case; a *disabled* snippet hides the ones of the earlier sources). `BuiltInSnippets` holds the snippets that ship (descriptions are localized through `Str.Editor.Snippet.<Key>`, `SnippetDescriptions`); none uses a word of the block completion, and `SnippetValidator` refuses those words (`KeywordExpander.IsKeyword`: `if`, `while`, `proc`...) so the legacy Tab behaviour is never shadowed. `SnippetImporter` turns the `<d>` / `<s>` / `{placeholder}` / `<cr>` code templates of the functions tree (`userfunctions.ini`) into snippets.

**Expansion.** `SnippetTemplate.Parse` reads a body (`${1:default}` with nesting, `${1}` mirrors, `$0`, the variables of `SnippetVariables`, `\$` and `\\` escapes) and lists the mistakes (`SnippetProblem`: unterminated or invalid placeholder, unknown variable, empty body); a mistaken part is plain text, so a snippet with a problem still works. `SnippetExpander.Expand` is pure: it fills the variables of the `SnippetContext` (`$CURRENT_PROCEDURE`, `$FILE_NAME`, `$SCRIPT_NAME`, `$DATE`, `$TIME`, `$SELECTION`), indents every line after the first like the line of the insertion (a tab at the start of a body line is one indentation level: tabs or spaces as the editor is set up), uses the line break of the document and returns the text with the places of the stops (`SnippetExpansion`). Everything above is tested without a window (`FalloutScriptStudio.Core.Tests\Snippets`).

**Editor.** `SnippetController` (`Editor\Controllers`, owned by `InputController`): `TryExpandTrigger` (Tab after a trigger word, outside comments and strings, not in the middle of a word; a legacy keyword goes to `TryCompleteBlock` first and wins) inserts the expansion in one `RunUpdate` (one undo step) and starts a *session* when there are stops: every stop occurrence is followed by `TextAnchor`s, the first stop is selected, Tab / Shift+Tab (`MoveToNextStop` / `MoveToPreviousStop`) move between stops (after the last one the caret goes to `$0` and the session ends), typing in a stop copies its text to its mirrors in the undo step of the typing, Esc or a caret that leaves the text of the snippet ends the session. The completion list adds the snippets whose trigger starts with the prefix (`AutosuggestKind.Snippet`, `CompletionSource.GetItems` with the snippets, `ScriptCompletionData` expands the snippet instead of inserting the trigger). `EditorCommand.InsertSnippet` (Ctrl+J) and `SurroundWith` (Ctrl+Shift+J, selection required, only the snippets that use `$SELECTION` are offered) ask `IWorkspace.PickSnippetAsync` for a choice; the list is `SnippetPickerViewModel` / `SnippetPickerWindow` (the pattern of the symbol list: filter box, arrow keys while typing, `FuzzyMatcher`, trigger matches first), opened through `IToolWindowService.PickSnippetAsync`. The manager is `SnippetManagerViewModel` / `SnippetManagerWindow` (Code > Manage Snippets..., button in Settings > Editor): rows for the project's, the user's and the built-in snippets, add / duplicate / delete / customize (a user copy with the same trigger replaces a built-in snippet) / disable, a check of the trigger (empty, too long, characters, reserved word, duplicate in the same file) that blocks the save and of the body that only warns, a body editor with the highlighting of the script (`SnippetBodyEditorSession`), import and export of a snippet file, import of the functions tree, and a save that writes the two files through `ISnippetService.TrySave`.
