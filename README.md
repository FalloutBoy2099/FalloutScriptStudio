# Fallout Script Studio (by Kain)

SSL script editor for Fallout 1/2 (sfall) — a complete rewrite in **.NET 10 / WPF / Fluent UI (WPF-UI)** of the legacy *Sfall Script Editor* (WinForms).

## Features

- AvalonEdit editor: SSL/MSG syntax highlighting (light / dark / system themes), procedure folding, auto-completion, tooltips (opcodes, macros, procedures, messages), indentation, block completion (Tab), comments, formatting, rename, references, Back/Forward history.
- Script analysis: native sfall `parser.dll` shipped in `resources\` (exact procedures, variables, references and includes), with the built-in C# parser as a fallback.
- Compilation / preprocessing / round trip / mass compilation (through `compile.exe`; mcpp or wcc optional). Every long operation shows what it does in the status bar and can be cancelled (button, Esc in the log panel, Ctrl+Break): the tool processes are killed and their files cleaned up.
- **Incremental builds**: "Build Changed" (Compile menu) compiles only the open scripts that are stale, and Mass Compile skips the scripts that are up to date (option "Mass Compile: Only Changed Scripts", on by default; "Rebuild All" forces everything). A script is up to date when its compiled `.int` is the one the last successful build produced from the same source, the same `#include`d files (followed through nested includes), the same compiler options and the same `compile.exe` / preprocessor; the build cache `fss-build.json` (in the project folder, otherwise next to the settings) is checked with the size and time stamp of every file, a damaged or locked cache just means a full rebuild, and a failed compilation is never remembered. The status bar shows "Compiling x (3/12), 9 up to date" and the result is summarized as "12 compiled, 9 up to date, 1 failed".
- **Compile profiles**: named sets of compiler options ("Debug" and "Release" to begin with: optimization, short-circuit, backward compatibility, debug information, preprocessor definition), kept in the settings and, per mod, in `fss-project.json`. The profile chosen in the toolbar is applied on top of the global and project options and changes only the options it sets; switching it makes the scripts stale, so "Build Changed" rebuilds them. They are edited in Options > Settings > Compiler and in the project settings.
- One list of problems (Errors tab): compiler and parser messages, missing tools, files that cannot be opened or saved, damaged settings... grouped and filterable, with a fix hint and a link to the right settings page; Ctrl+F8 / Ctrl+Shift+F8 go to the next / previous problem and the status bar counts them. With nothing to report the tab shows a friendly "No problems" text instead of an empty grid, and its columns keep a readable minimum width.
- **No external executable is needed to read `.dat` archives (Fallout 1 & 2) or to decompile `.int` scripts**: the DAT reader and the decompiler are written in C#. An external `int2ssl.exe` can still be plugged in (Options → Compiler → Decompiler).
- `.msg` file editor, registration in `scripts.lst`, advanced search in files.
- Dialogue node flowchart (`.fcd` compatible), node code editor, dialogue preview / test, dialogue function rules.
- **Script <-> message file consistency** (Dialogue > Check Messages, Ctrl+Shift+M; also after a save, *Settings > Messages > Check messages on save*): the numbers a script shows (`NMessage(100)`, `Reply(...)`, `NOption(101, node, 4)`, `mstr(n)`, `message_str(...)`, `floater(n)`, sums such as `MSG_BASE + 5`, `random(a, b)`) are compared with the lines of its `.msg` file. Unknown numbers are errors at the line of the script, with a *Add the missing messages to the message file* fix that appends `{n}{}{}` lines (atomic write, the open tab or the Message Editor stay in sync); duplicate numbers are errors, empty used messages warnings, unused messages and missing female variants (+1000) are notes at the line of the message file; a script that uses messages without a message file gets one problem with a *Create or associate the message file* link.
- **Preview Dialogue From This Node**: right-click a node procedure (name contains `node`, or `talk_p_proc`) in the Procedures panel, in the editor (Ctrl+Shift+P, also in the Dialogue menu) or on a node of the flowchart to open the dialogue preview positioned at that node; a preview window that is already open for the script moves to the node and Back returns to where it was.
- **Dialogue quality check** (Dialogue > Check Dialogue, Ctrl+Shift+Q; also after a save, *Settings > Messages > Check the dialogue on save*): the dialogue graph of a script (nodes = procedures whose name contains `node`, and `talk_p_proc`; options, `call` statements and every other mention of a node name) is checked for nodes that nothing leads to, replies with no option and no exit (a dead end where the player would be stuck), options that jump to a procedure the script does not define (error), groups of nodes that only lead to each other with no way out, nodes with options but no text, two options to the same node, nodes whose message numbers the message file lacks (linked to Check Messages, not repeated), nodes with more than 8 options and two options that show the same message. The conventions are the Fallout 2 ones (`Node998` combat, `Node999` exit, `Node1000` barter, code-only nodes, `end_dialogue` / barter / attack calls end the dialogue) and the check is conservative: a node name mentioned anywhere counts as a link, so a statement the parser does not know never causes a false alarm. The findings are problems of the Errors tab (source Parse, with the node names, a click goes to the line, republished after a parse while the text is unchanged); the nodes of the **flowchart** get a ring and a badge (a cross, an exclamation mark or an "i", so the colour is not the only signal), unreachable nodes are faded, the tool tip lists the findings, and the toolbar button *Issues (n)* opens an accessible list that jumps to the node.
- **Compare Message Files** (Dialogue > Compare Message Files..., the Message Editor "open with" menu and the context menu of a `.msg` tab): pick an original `.msg` (the current one, or the message file of the current script; the language is the folder below `text`) and the translations (the `text\<language>\<same path>` files of the other languages are offered automatically, others can be added). A virtualized, keyboard-friendly table lists the messages by number with the original text, the translated text and a status (missing / extra in the translation, same text = not translated, differs only by placeholders or tags, empty, player marker or description differs, OK), toggles per status with counts, a filter box and "only lines with issues"; the likely mistakes are flagged (other `%s` / `%d` conversions, `<...>` / `@...@` tags or `$...$` variables, white space only, trailing spaces, characters that no code page gives, mixed encodings). Double click or Enter opens the line in the Message Editor on its message. *Add missing lines* appends the original messages the translation lacks (after the last line, existing lines untouched, same encoding, byte order mark and line breaks, atomic write, optional `# TODO: translate` comment, text that the code page of the file cannot hold is left out and reported), *Copy numbers*, *Export report* (CSV or text) and *Show as problems* work on the lines listed. The files are read with the encoding of the settings for the original and detected (byte order mark, UTF-8, then the code page of the language: Windows-1252, 1250, 1251, cp866 by the legacy option...) for the translations. A 30 000 line file compares in about 100 ms.
- **Live semantic diagnostics** (while you type, in the background, *Settings > Editor > Semantic analysis while typing*: Off / Errors only / Errors and warnings): the mistakes that `sslc` would only report when the script is compiled are underlined with a tool tip and listed in the problems with their file and line: a wrong number of arguments (default values and forward declarations taken into account), an unknown name (with *Did you mean ...?*), a procedure used before its definition or forward declaration, a variable used before its declaration or outside its procedure, an assignment to a constant, a procedure or variable declared twice, a `begin` without `end`, an `if` without `then`, a `while` without `do`, a procedure started without `call`, a procedure declared and used but never defined. Calls of the engine and sfall functions are compared with `opcodes.txt` / `functions.ini` (number of arguments, a string given for a number). **Ctrl+.** (Quick Fix, also in the Code and context menus and as a link in the problem) applies the fix under the caret: the nearest name of a typo, the missing forward declaration, the removal of a repeated declaration. Every rule is checked against the real compiler by the tests, and the analysis never reports an error for a script the compiler accepts (a header it cannot read or a macro that may declare names makes it stay quiet).
- **Command palette** (F1, View > Command Palette; Ctrl+Shift+P is the editor's Preview Dialogue From This Node): one keyboard-first list of every command of the application: all the menu commands with their menu path ("Code > Format Document"), the editor commands that have no menu item, the settings that are on or off, the themes, languages, compile profiles and definitions, the recent files and projects, the templates. Type to filter (a name that starts with the text, then a word that starts with it, then letters in order; case and accents are ignored, several words must all match); the last ten commands used come first; each row shows the shortcut and the state, a command that cannot run now is dimmed with the reason ("Requires an open script") and cannot be chosen. Up / Down / Enter / Esc; the palette closes before the command runs, so the focus is back in the editor.
- **Replace in Files** (Edit > Replace in Files..., Ctrl+Shift+H, or the button of the search window): replaces text in the current script, the open scripts or the files of a folder (masks, subfolders), with case, whole word and regular expressions with groups (`$1`). Nothing changes before a **preview**: a tree of the files with their replacements, each shown as the line before and after, a check box per file and per replacement (tri-state files), a summary ("42 replacements in 7 files") and **Replace Selected**. Open documents are edited as one undo step (and stay unsaved); the other files are rewritten in their own encoding with their byte order mark and line breaks, through a temporary file; a file that changed since the preview, a read-only or a locked file is left untouched and reported as a problem, never half-written. **Edit > Undo Last Replace in Files** puts back what the run changed in every file that was not modified since.
- **Configurable code formatting** (Settings > Editor > Code formatting, with a live preview of a sample script; per project in the project settings): the indentation (tabs or spaces, width), a rebuild of the indentation from `begin` / `end`, continuation lines (levels, or aligned to the bracket), where `begin` goes (same line as `then` / `do` / the procedure, or its own line), `else begin` joined or split, where `else` goes, spaces around operators, around `:=` and after commas (add / remove / keep), spaces inside parentheses, blank lines between procedures and the longest run of blank lines, trailing white space, a final line break, aligned `#define` values and an optional maximum line length that wraps long argument lists. The defaults reproduce the original formatter byte for byte; strings, comments, `#include` lines and the line breaks (CRLF / LF) are never touched, formatting twice gives the same text, and only white space changes (the tests compile the samples before and after formatting with the real compiler and compare the compiled files). **Code > Format Project...** previews the files that would change (project folder with masks `*.ssl;*.h`, or the open documents) with the number of changed lines and a before / after view of the selected file, a check box per file, and formats the checked ones with the safe rules of Replace in Files (a file that changed since the preview, a read-only or a locked file is left alone and reported; open documents are edited as one undo step; the other files keep their encoding, byte order mark and line breaks; cancellable). **Format on save** (off by default) formats scripts and headers when they are saved.
- **Snippets**: a trigger word followed by Tab expands to a piece of code with tab stops (`${1:name}`, `${2}`), mirrors (`${1}`), a final caret (`$0`) and variables (`$CURRENT_PROCEDURE`, `$FILE_NAME`, `$SCRIPT_NAME`, `$DATE`, `$TIME`, `$SELECTION`), indented like the line it is typed on with the tabs or spaces of the settings and the line breaks of the document. Tab and Shift+Tab move between the stops, typing in a stop updates its mirrors, Esc leaves snippet mode and the whole expansion is one undo step. The completion list offers the snippets whose trigger starts with what you typed; **Code > Insert Snippet...** (Ctrl+J) opens a filterable list and **Surround With...** (Ctrl+Shift+J) wraps the selected code with a snippet that uses `$SELECTION`. Built-in snippets (procedure, if / else, while, for, foreach, call, display_msg, dialogue nodes, variables, `#define`) can be replaced or disabled; your own live in `snippets.json` in the settings folder and a project can have `fss-snippets.json` (project over user over built-in). **Code > Manage Snippets...** (also in Settings > Editor) adds, edits, duplicates, deletes and disables snippets with a code editor for the body, checks the triggers and the placeholders, imports and exports snippet files and turns the code templates of your functions into snippets. The block completion of the legacy keywords (`if`, `while`, `proc`...) keeps its Tab behaviour.
- Function tree (`functions.ini` + user functions), project explorer, import of the legacy settings (`settings.dat`).
- **Projects**: a mod folder can hold a `fss-project.json` that overrides, for that mod only, the headers / output / message folders, `scripts.lst`, the preprocessor and its definitions and the compiler flags (each option either inherits the global setting or overrides it; paths are stored relative to the project). File > Open Project / Recent Projects / Close Project, a hint when an opened script belongs to another project, the project name in the status bar and the window title. `fss-project.json` is **watched**: a hand edit (or a save by another editor, a `git pull`) is reloaded at once without restarting, with a notice in the status bar; an invalid edit keeps the last valid settings and is reported as a warning with the line and column and a link to the file; deleting the file reverts to a folder without settings. The Settings window marks every option the open project overrides ("Overridden by project X", the global control dimmed, a link "Edit project setting" that opens the project settings on that option), the project settings window can reload the file or open it in the editor, and the documents that were open in a project are remembered and opened again with it (option "Restore the open files of a project", a hint with a "Restore open files" link when other documents are open).

- **Project-wide navigation**: F12 (definition), Ctrl+F12 (declaration) and Alt+F12 (references) also work across the whole project. A symbol that is not defined in the script or in its includes (a procedure of another script, a macro of a header the script does not include, an `import`ed procedure or variable) is looked up in a background **project index** (the project folder, or the folders of the open scripts, plus the headers folder; incremental, rebuilt on save and on project change, progress "Indexing 1200/5000" in the status bar). When a name is defined several times a small list offers the places, the nearest first (the current file, the files it includes, the same folder). **Ctrl+T (Go to Symbol)** lists the procedures, macros and variables of the whole project with their kind, file and line; type to filter (prefix, then start of a word, then any part of the name), arrow keys and Enter open the symbol.
- **More refactorings** (Code menu, context menus of the editor and of the procedures / variables panels): *Delete Unused Procedure* (previews the procedure with its comment and forward declaration, refuses when the project still uses it or when the game calls it), *Find Unused Variables* (locals, arguments and script variables that are never used or never read, listed as information problems with a *Remove the declaration* fix; optional faint dotted mark in the editor with *Settings > Editor > Mark unused variables*) and *Extract Procedure* (Ctrl+Shift+E: selected complete statements become a procedure placed before the current one, the variables they use become parameters, a single changed variable is returned). Each one is a single undo step.
- **Global variables tracker** (right browser > *Globals*, View > Show Global Variables): every read and write of the sfall globals (`set_sfall_global`, `get_sfall_global_int` / `_float`), the game variables (`global_var`, `GVAR_*`...), the map variables and the local variables of the whole project, grouped by family, with the macros resolved (`GVAR_FOO` and `27` are one variable), the procedure and the literal written, a filter, double click to go to a use, Find all, Copy name, Ignore and an export to CSV. **Code > Check Global Variables** (or *Settings > Editor > Global variable findings* after each update, off by default) lists in the problems the variables that are written but never read (information), read but never written (warning; the variables the engine sets and your ignore list are left out), used as an integer and as a float, probable typos in names (*Did you mean ...?*) and sfall names that are not exactly 8 characters long or start alike.
- **Function help**: **Ctrl+F1** (Code > Function Help, context menu, command palette) opens a popup with the documentation of the function, opcode, macro or procedure under the caret: the typed signature, the description of `opcodes.txt` / `functions.ini` (the arguments of a hook, the category in the functions tree), the comment above a procedure or macro of your project, and a button that opens the page of the online sfall documentation (only that site is ever opened). The hover tips end with a small "Ctrl+F1 for help" when help exists. The **Help** tab of the right browser shows the same documentation for the word under the caret as you move, has a filter to browse all the functions and the buttons Copy signature and Insert call.

## Structure

| Folder | Role |
|---|---|
| `FalloutScriptStudio` | WPF application (x86) |
| `FalloutScriptStudio.ParserHost` | Small x86 console process that runs the native `parser.dll` (a crash of the DLL only kills that request, not the editor) |
| `FalloutScriptStudio.Core` | Business logic without UI (parsing, compilation, DAT, decompilation, messages, dialogues, refactoring, settings) |
| `FalloutScriptStudio.Tests`, `FalloutScriptStudio.Core.Tests` | xunit tests |
| `FalloutScriptStudio.UiTests` | Smoke tests of the real program: it is started off-screen (UI test mode) and driven through UI Automation; skipped unless `FSS_RUN_UI_TESTS=1` |
| `scripts` | `Run-UiSmoke.ps1`, which runs the UI smoke tests |
| `docs` | `CONVENTIONS.md` (code style enforced by `.editorconfig`), `ARCHITECTURE.md`, `HOW_TO.md` (developer how-to), `GLOSSARY.md` (the common terms of the 11 languages) |

**Developer how-to:** [docs/HOW_TO.md](docs/HOW_TO.md) lists, step by step, the files and tests to touch to add a menu command with a shortcut, a setting, a language or a localized string, a problem producer, an editor command, a test file, a parser/compiler option, and how the release is published.

**Translators and authors of UI texts:** [docs/GLOSSARY.md](docs/GLOSSARY.md) lists the canonical translation of the ~60 domain terms (procedure, node, header, compile, flowchart...) in the 11 languages; a test fails when a translation does not use them.

## Build

```
dotnet build FalloutScriptStudio.sln
dotnet test FalloutScriptStudio.Core.Tests
dotnet test FalloutScriptStudio.Tests
```

The application is built for **x86** (the native `parser.dll` is 32-bit). The application never loads `parser.dll` itself:
`FalloutScriptStudio.ParserHost.exe` (next to the executable, copied by the build and by `Publish.ps1`) hosts it in a separate process,
which is restarted automatically after a crash; after 3 crashes in a row the native parser is turned off for the session and the built-in
C# parser takes over.

`Publish.ps1` produces in `publish\`: `FalloutScriptStudio.exe` (needs the .NET 10 x86 runtime), `FalloutScriptStudio-NET.exe` (runtime included) and
`FalloutScriptStudio.ParserHost.exe` (self-contained, shared by both), plus `descriptions\` and `resources\`.

### UI smoke tests

`.\scripts\Run-UiSmoke.ps1` starts the real program (a private copy of the build output, with `FSS_UI_TEST=1`) and drives it through UI Automation: the windows are
placed outside of the monitors and never take the focus, so you can keep working. The pictures and the report go to `_test_files\work\ui-smoke\` (git-ignored).
A plain `dotnet test` skips these tests. See `docs\HOW_TO.md`, guide 14.

### Integration tests with the real tools

The tests in `FalloutScriptStudio.Core.Tests\Native` run the real `parser.dll`, `compile.exe` and `int2ssl.exe` (copies in
`_test_files\tools`, overridable with `FSS_SSLC_DIR`) on real scripts (`_test_files\samples`, overridable with `FSS_SSL_SAMPLES`).
Every file the tests use or create stays in `_test_files` (see its `README.md`), never in `%TEMP%`; `_test_files\work` is the git-ignored scratch folder.
When the tools or the optional sample sets are missing the tests are **skipped**, not failed.
